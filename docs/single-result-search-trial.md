# Single-result search trial

Only the server-confirmed `ckunkel2` login automatically opens a product when WebTrack reports exactly one native search result. Product-code, UPC and descriptive searches follow the same rule. Multiple results and zero results retain the normal search page and existing search suggestions.

The client requires an explicit native result total, deduplicates image/title/review links by product ID, excludes recommendation cards, and accepts only the same-origin ProductDetail.aspx destination. One card on a later page of a larger search cannot trigger navigation. Grid and list product links are read from the native results panel.

Before navigation, a fresh same-origin GET of AccountSettings.aspx must contain the native signed-in marker and matching user headings for ckunkel2. No local-storage ID, cached login or query flag enables the trial. Missing identity, request timeout/failure, another account, an expired session, user input during verification, changed results, or an embedded page leaves native results usable. The intermediate search history entry is replaced so Back does not immediately redirect again. Product destinations omit WebTrack’s returnUrl parameter, avoiding a native Back link to the intentionally skipped single-result page.

Search priority update (build 20261016-3): the existing header also loads the search client on signed-in pages. A fresh account check warms an eligibility hint while the shopper is on the source page. Only a verified ckunkel2 page intercepts header Enter/search-button actions. Every intercepted search performs another fresh identity check in parallel with a GET of the native search response; the earlier hint never authorizes navigation. The response is parsed as inert HTML. A single match opens its product directly, without creating an intermediate results document or running its quote/Quick buy scripts. Multiple or zero matches navigate to the normal results URL. Those fallback cases perform an additional results GET before navigation. Failed lookups use the normal results URL; existing result-page recovery remains available.

Editing the query, leaving the search field or clicking elsewhere cancels an outstanding direct lookup. Repeated Enter does not create multiple lookups. A direct jump preserves the sanitized search analytics event through the existing analytics runtime; multi-result searches remain measured on their normal results page. The direct route waits for native search and current-account responses, so it still includes server response time.

Scope: smart-search.js build 20261016-3 and its existing headermodern.js loader version. No cart, checkout, payment, account-setting writes or added dependencies.

Validation: 435 automated tests pass, including 20 initial redirect/gating cases and 12 direct-routing cases plus native return-link normalization. A delayed-response local Chrome fixture recorded the one-match response as a data fetch, zero intermediate results documents, zero enhancement-script loads before the product, and a direct product navigation. Search button, multiple matches, other-account and guest behavior were checked in the browser. Local Chrome checks verified a real navigation for the synthetic ckunkel2 session, normal results for a synthetic other account and guest, the 64-result case, and Back without a loop. Live baseline searches verified 24082ypl returns product 6698 and YPL returns 64 matches. Live post-release verification is recorded in the project checkpoint.
