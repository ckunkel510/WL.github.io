# Optional cart substitutions

Customers with a verified shortage at their account's currently selected store can open **Find a substitute** from that cart line. They can keep their original items and proceed with the existing pickup estimates at any time. Suggestions and history failures do not gate native Proceed or change pickup/date/order/payment rules.

Customers choose the whole line or only the quantity unavailable locally. Each alternative shows its listed similarities, specific differences, freshly checked local stock, current signed-in native unit price and estimated merchandise change. The customer selects an option, reviews its differences and explicitly applies it. Existing quantities of the alternative count against its available stock. Original and replacement units must both be individual pieces; there is no implicit pack, linear-foot, cutting-service or coverage conversion. Quantity pricing and tax are recalculated by WebTrack in the resulting cart.

## Eligibility and catalog scale

The initial automatic family is untreated dimensional lumber. Thickness, width, full category, listed species/grade, brand and every remaining title qualifier must match; length must increase. Treated, engineered, decking, fencing and insufficiently specified products are excluded from automatic matching. A stud-grade qualifier is retained. Backend catalog titles are rechecked against fresh native product titles before an option can apply. The broad PDP recommendation shelves remain separate and unchanged.

`data/approved-substitutions.json` holds explicitly reviewed directional pairs with enabled, from, to, reason and differences fields. It starts empty. New families or non-lumber equivalents can be reviewed and added without accepting broad category similarity as equivalence. Missing matches leave the customer's original checkout available. Configured, ambiguous duplicate, unmanaged-unit and pallet lines are excluded; the optional parser is bounded to 60 cart lines.

## Native cart update

The client rechecks the complete native cart, account store, both stock tables, current native product titles and customer prices immediately before writing. Changed quantities, price, store, local allocation or aged review require a fresh customer review. The native replacement AddProductButton is posted first. Only an exact read-back of the expected complete cart permits the original line's native refQty or del postback. Unrelated fields, native view state and Telerik quantity state are preserved. Only native product-add and individual cart-line targets and same-origin form actions are permitted; no checkout/order/payment control is used.

A lost POST reply triggers a read, never an automatic resend. A failed source reduction is compensated only while the complete cart exactly matches the known add-only state; pre-existing replacement quantities are preserved. Concurrent or unreadable state instead requires reviewing the actual cart. A temporary unload warning protects an actively requested swap, and a browser lock prevents this feature from running twice concurrently. WebTrack does not expose an atomic replacement endpoint: a browser crash or leaving mid-request can still leave an intermediate cart requiring review. No automatic substitution or checkout submission occurs.

`ShoppingCartRow.js` loads the isolated module asynchronously only after ordinary signed-in cart cards are ready. `PickupAvailability.js` is reused as a read-only parser. The dormant `wl-shoppingcart.bundle.js` is unchanged; the observed runtime uses individual scripts. Failed optional script delivery leaves native cart and checkout controls alone.

## Accepted choices and future ranking

The API issues an opaque one-use offer receipt lasting fifteen minutes. After an exactly verified cart swap, the browser submits that receipt plus scope, quantity and public store name, best-effort and without delaying the refreshed cart. The server revalidates the directed pair against the current catalog and rules, then atomically consumes the receipt, increments a product-pair total and appends a bounded anonymous event record. Retry cannot increment twice. Receipt recording is client-attested cart-selection evidence, **not** proof of a paid order, fulfilled substitution or staff approval.

The existing Upstash Redis connection is reused; no new dependency, service, secret or environment value is required. Production keys use `wl:substitutions:v1:`; non-production deployments use `wl:substitutions:preview:v1:`. Tests force in-memory storage even if Redis credentials exist. Pair totals are durable. The `recent` list retains the latest 10,000 records, containing only product IDs, rule, scope, quantity, public store, timestamp and evidence/fulfillment flags. No account, customer name, email, order identifier, free text, price, cost, margin, token or payment information is accepted into these records. These keys can be reviewed through the existing private Redis console; there is no public history-listing endpoint.

Counts modestly boost already eligible candidates at suggestion time. They never create a new equivalence, infer a reverse pair, bypass a rule or assert fulfillment. Origin checks, content/size/quantity/store validation, one-use receipts and bounded in-memory request limits reduce accidental and repeated submissions. As a public storefront signal, popularity is not an authenticated purchasing statistic.
